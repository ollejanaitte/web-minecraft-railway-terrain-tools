# ADR-012: Real 3D Rail Model Transition and Production Asset Contract

- Status: **Accepted / FREEZE**
- Date: 2026-08-12 JST
- Decision owner: Railsys Phase 1 Remaining Roadmap
- Supersedes: the repeated-rigid-segment baseline in
  `doc/content-system/RENDERER_CONTRACT.md` section 7 and any incompatible
  origin/model assumptions in the Phase 1.2.3 draft asset contract

## 1. Context

R9 proves JSON loading, registry lookup, fallback, multiple asset selection,
and visible gauge/rail/sleeper differences. Its production renderer already
combines shared-endpoint continuous rail spans with sleepers placed by real
distance `s[m]`. It does not yet load and render a production rail profile,
original textured sleeper mesh, or complete material/UV contract.

Persistence is not production-ready. This is the last low-migration point at
which to freeze asset identity, units, axes, deformation, and version fields.

## 2. Transition timing decision

| Option | Benefit | Main cost/risk | Verdict |
|---|---|---|---|
| A. Immediately after R10 | Real appearance arrives early and exposes authoring errors | If implementation begins before the contract is frozen, origin/axis/version decisions can churn alongside UX | NOGO as stated |
| B. After Persistence / Network | Topology can proceed independently | Persistence would store an unstable asset contract; later origin/version changes require save migration | NOGO |
| C. Immediately after the Production Rail Asset Contract is frozen, before Persistence | Exposes unit/origin/axis/deformation/WebGL problems before they enter save data | Requires a deliberate contract gate at the start of R11 | **GO / FREEZE** |

Operationally, R10 closes the normal-world placement UX. R11 then has two
ordered internal gates:

1. **R11-A: freeze this Production Rail Asset Contract;**
2. **R11-B: implement and validate the Real 3D Hybrid baseline.**

R12 Persistence may not begin until both R11 gates are GO. This is Option C;
it is not permission to start 3D implementation before the contract gate.

## 3. Rendering method decision

| Method | Curve/gradient/cant | Gaps and overlaps | Authoring | Web performance | Switch path |
|---|---|---|---|---|---|
| A. Repeated rigid 3D segment | Faceted; rigid parts fight twist and tight radii | Requires overlap or very short segments | Familiar full-segment model | Instance-friendly but high counts and visible repetition | Special rigid models still need topology |
| B. Fully dynamic continuous mesh | Best line continuity and cant deformation | Shared sections can be exact | Every part becomes procedural | Batchable, but poor fit for sleepers/accessories | Branch junction still needs special treatment |
| C. Hybrid | Continuous rail profile follows every frame; rigid parts use `s[m]` frames | Continuous rail keeps R5 shared boundaries; repeated parts have explicit spacing | Profile + reusable mesh parts | Continuous batches plus cached rigid meshes | Route-aware special assets can reuse both paths |

**Decision: Method C Hybrid is the Phase 1 production baseline.**

- left/right running rails are generated by extruding a real head/web/foot
  cross-section through consecutive `RailLocalFrame` sections;
- section vertices use each endpoint's own right/up frame, so gradient and
  cant/twist are not collapsed to one averaged up vector;
- sleepers, fasteners, and discrete accessories are original rigid 3D meshes
  placed by actual `s[m]`, never normalized-progress spacing;
- ballast/base may use a continuous deformable profile or a repeated part, but
  the asset declares which and the renderer keeps it appearance-only;
- a turnout is a future route-aware composition of branch geometry plus
  special asset parts; it is not a reason to move line mathematics into an
  asset.

The R5 Continuous Rail contract is non-negotiable. A fixed-length whole-track
model repeated along the path cannot become the production fallback.

## 4. Dependency invariant

The semantic data flow is:

```text
Geometry / RailPath / PathSample / RailLocalFrame / Cant
                     -> Production Renderer <- RailAsset appearance
```

Geometry-core does not import renderer, texture, model, registry, or game-world
classes. An asset may own local appearance definitions (cross-section, mesh
parts, material, texture, UV, placement pattern), but not world-space centreline,
curve, gradient, cant, topology, or path sampling. The renderer consumes the
immutable line and appearance inputs; it cannot rewrite either one.

## 5. Production Rail Asset Contract Freeze

### 5.1 Identity, version, and compatibility

- `schemaVersion`: integer pack schema; breaking fields increment it.
- `assetId`: stable lowercase namespaced ID; unique within the registry.
- `displayName`: user-facing label; missing value falls back to `assetId`.
- `assetVersion`: required asset content version. Persistence stores it with
  `assetId`; incompatible replacement does not silently reinterpret saved data.
- `railType`: `normal` in R11; `switch` is reserved for R14.
- `rendererType`: `hybrid-continuous-v1` for the Phase 1 production baseline.
- `compatibility`: minimum/maximum supported schema and renderer capabilities;
  unknown required capability rejects the asset and selects fallback.

### 5.2 Units, origin, and axes

- physical unit is **metre**; one Minecraft block is one metre;
- `scale` is an import transform, validated in `(0, 10]`; runtime geometry is
  already in metres and does not apply arbitrary per-path scale;
- canonical local axes are `+X right`, `+Y up`, `+Z forward`;
- the canonical asset datum is `(0,0,0)` on the path centreline at the support
  surface used by the current production-relative renderer;
- rail/sleeper vertices are authored above or relative to that support datum;
  an imported model's declared origin transform must normalize it to the datum;
- `gaugeM` is the distance between left/right rail-head centre lines, located at
  `x = +/-gaugeM/2`; it never changes the path centreline.

### 5.3 Continuous rail profile and mesh

- `railProfile` is a closed, ordered 2D cross-section in local `(right, up)`
  coordinates and represents visible head, web, and foot rather than a box;
- left/right rail meshes are derived by profile extrusion along path sections;
- adjacent sections reuse the same sampled frame and boundary vertices;
- winding, normal direction, seam, and cap rules are deterministic;
- UV contract: `U` is accumulated physical distance `s` and `V` is normalized
  profile perimeter distance; texture repeat is declared in metres;
- curve, gradient, and cant come exclusively from `PathSample` and
  `RailLocalFrame`; deformation preserves gauge in each local frame;
- mesh output is a cache, not authoring state or persistence data.

### 5.4 Sleeper and accessory meshes

- `sleeperMesh` is an original rigid 3D mesh in canonical axes;
- sleeper placement is `phaseM + n * spacingM`, clamped to path length;
- sleeper dimensions, overhang, and vertical relation to the running surface
  must validate against gauge and the asset datum;
- fasteners and accessories use the same real-distance placement contract or an
  explicit attachment to a sleeper instance;
- rigid parts rotate with the full local frame, including cant, but do not own
  or approximate the centreline.

### 5.5 Materials, textures, and UV

- R11 must include at least one original Railsys material and PNG texture, not
  only flat debug colours;
- at least rail and sleeper materials are distinct;
- missing texture resolves to a visible built-in checker/error material with a
  warning; it never makes the rail invisible or crashes;
- material/texture paths are pack-relative and cannot escape the pack root;
- no asset-provided executable script is supported in Phase 1;
- UV and material batching must be deterministic under TeaVM/WebGL.

### 5.6 Fallback and validation

- the built-in fallback is a valid `hybrid-continuous-v1` asset with a visible
  continuous rail profile and sleeper mesh;
- missing asset ID, unsupported version/capability, invalid mesh/profile,
  missing required part, or parse failure resolves safely to fallback;
- validation covers finite values, gauge `[0.6, 1.8]m`, positive dimensions and
  spacing, distinct axes, valid indices/winding/UVs, texture limits, and
  reasonable extents;
- malformed optional parts are skipped with a warning; malformed required
  running rails reject the asset;
- pack loading is deterministic and idempotent.

### 5.7 LOD, sectioning, rebuild, and cache

- R11 supplies one production LOD plus a fallback LOD contract; advanced LOD
  authoring may be deferred, but distance selection cannot alter RailPath;
- mesh sections align to renderer spatial/chunk sections and share exact path
  boundary samples to avoid cracks;
- edit invalidation is limited to affected path/asset sections;
- cache key includes rail definition identity/revision, `assetId`,
  `assetVersion`, LOD, and renderer format version;
- caches are never persisted and may be discarded at any time;
- no GL state or buffer object is stored in geometry-core.

### 5.8 Performance and Web constraints

- target platform is TeaVM/WebGL; no runtime dependency on desktop-only model
  parsers or arbitrary filesystem access;
- meshes/textures are loaded once per content hash and reused;
- renderer batches by material/section and does not issue a state change per
  sleeper;
- the R11 reference gate records warm p50/p95 renderer time and FPS for a 500m
  mixed straight/curve/gradient/cant fixture with at least 250m visible;
- minimum R11 acceptance is 30 FPS and rail-render p95 at or below 5ms on the
  recorded reference environment, with no unbounded frame-to-frame allocation;
- if the reference environment cannot meet this honestly, R11 is NOGO and the
  measured budget must be reviewed before feature scope expands.

### 5.9 Clean-room policy

All R11 model/profile/mesh/material/texture assets are newly authored for
Railsys with provenance recorded under `doc/`. RTM/NR01 code, models, textures,
sounds, scripts, or pack assets are not imported, converted, traced, or
committed. Public behaviour and generic directory/field concepts may inform the
contract only.

## 6. Persistence boundary

After R11, R12 persists:

- stable rail/piece/network identity;
- authoring anchors and geometry parameters;
- cant profile inputs;
- `assetId` and `assetVersion`;
- topology-compatible reserved identity fields and user metadata; full
  connection topology and turnout route state are added by R13 and R14;
- schema/renderer contract versions needed to regenerate safely.

R12 does not persist `RailPath` samples, generated vertices, GPU buffers,
textures, or caches. Load resolves assets, applies a documented fallback when
needed, reconstructs RailPath from authoring inputs, and rebuilds render meshes.

## 7. R11 scope and gate

### In scope

- freeze and implement the contract above;
- original profile-based running rail and original sleeper 3D mesh;
- original texture/material and UV pipeline;
- straight, curve, gradient, cant, and continuous boundary behaviour;
- at least two assets with visible structural differences;
- fallback/missing/corrupt pack behaviour;
- section rebuild/cache and a recorded WebGL performance baseline;
- numerical, harness, build, GUI, screenshots, vision, and R5-R10 regression.

### Out of scope

- persistence implementation, connected networks, turnout implementation;
- train, signals, stations, catenary;
- asset scripts, proprietary import, advanced external pack distribution;
- diamond/slip/crossing assets and full multi-LOD art pipeline.

### GO

- asset contract and implementation agree;
- profile/mesh/material/texture are visibly real 3D and clean-room original;
- same RailPath produces correct straight/curve/gradient/cant for two assets;
- gauge remains correct in every local frame and shared section boundaries have
  no visible or numerical crack;
- fallback is visible and non-crashing;
- performance gate passes; harness/build/regressions pass; GUI and vision show
  no corruption.

### NOGO

Any contract/implementation mismatch, return to rigid repeated whole-track
segments, path mutation by an asset, discontinuity, incorrect cant/gauge,
missing real texture/material evidence, unsafe fallback, performance gate
failure, or regression keeps R11 NOGO.

## 8. Consequences

Option C reduces persistence migration risk and forces Web-specific model
problems to surface early. Hybrid rendering preserves the mathematical work
already proven in R5-R9 while enabling authored 3D sleepers and materials. It
also creates more up-front contract and mesh-validation work; that cost is
accepted because it is lower than migrating saved worlds later.
