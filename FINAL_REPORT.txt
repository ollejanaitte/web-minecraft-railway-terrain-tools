9. CURRENT /railsys RE-ANALYSIS
====================================================================
Re-read all rail sources (rail/*.java, CommandRailSystem, EntityRailVehicle,
ItemRailWand, RenderRailVehicle, integration points). Findings match prior
analysis:
- Model: node/segment graph + per-entity segmentId/progress[0,1]; raw-t
  Bezier; static graph mirror; per-world WorldSavedData.
- Movement: lead advances progress; followers copy leader's segment each
  tick with modulo wrap -> the known follower teleport/disappearance bug.
- No pitch/roll, no bogies, no distance model, no client graph sync, no
  content system, debug-block rail visuals.
v1 strengths worth keeping: graph adjacency, station/switch/route concepts,
testloop/testline/testcurve builders, debug rendering, 4-point RailWand
Bezier creation, WorldSavedData persistence pattern, entity+command wiring.

12. SCALE / COORDINATE
====================================================================
1 block = 1 m. World +X east / +Z south / +Y up. Train local: +Z forward,
+X right, +Y up (forward axis configurable per def; default +Z).
Yaw 0=+Z, cw-positive, wrap [-180,180); pitch +up; roll +right-down.
Speeds m/tick (km/h / 72 = m/tick [R-I]); accel m/tick^2 (km/h/s*0.0006944
[C-MP]). Doubles for position; floats per-frame; EPS=1e-6. Supports
10/16/18/20m cars, trams, locomotives, freight (sizing targets in
architecture doc).

====================================================================
13. RAIL ARCHITECTURE
====================================================================
Separation of: RailGeometry (shape, immutable), RailPiece (geometry + world
blocks + state + network refs), RailNetwork (registry + adjacency + route +
signals/stations/crossing/catenary), RailPath/PathPosition (route history +
distance resolver), RailSwitch (piece with branch geometries), RailRoute
(planned route), RailDefinition (content). Data ownership and flows in
doc/architecture/DATA_MODEL.md + diagrams.

====================================================================
14. RAIL GEOMETRY API
====================================================================
RailSample{x,y,z,tangent,yaw,pitch,roll,curvature,gradient,cant,distanceM,
pieceId,dir,progress}. API: length(), sampleByDistance(d), sampleByProgress,
nearestDistance(x,z), point/yaw/pitch/roll/curvature at distance,
sampleAll(split), branches(). Continuity is the acceptance criterion.
Pseudo-interface in doc/architecture/RAIL_GEOMETRY_DESIGN.md.

====================================================================
15. ARC LENGTH
====================================================================
Straight exact; Bezier adaptive polyline, base split=clamp(round(len*32),
8,384) [R-I]; ArcLengthTable (cumulative metres + reparameterized param);
distance->progress binary search; cache per piece (lazy, invalidated on
edit); nearest via one pass; memory tiny; huge networks via ActiveRailCache.

====================================================================
16. LINE TYPES / CANT
====================================================================
Straight (horizontal + constant gradient), Curve (horizontal cubic Bezier),
Vertical curve (vertical Bezier, smooth pitch), Switch branches, optional
Turntable. Cant profile per-distance roll (center/edge cant concepts
[R-I]); body lean from geometry roll. Acceptance: x/y/z/yaw/pitch/roll
continuous everywhere.

====================================================================
17. SWITCH / TURNOUT
====================================================================
Conclusion: switch is REAL GEOMETRY (branch sub-geometries + state), not a
"next segment id". Planned types: basic turnout, single cross, scissors
cross, diamond cross [R-I taxonomy]. Handles facing/trailing/reverse;
formation follows the active branch via shared path (no follower
divergence); persistence + sync + signal/interlocking hooks.

====================================================================
18. TRAIN ARCHITECTURE
====================================================================
TrainFormation (ordered cars, controller, path, leaderDistance) / TrainCar
(def ref, front/rear Bogie, pose, couplers, TrainState) / Bogie (logical
anchor) / Coupler / TrainController (notch physics) / TrainDefinition
(content) / TrainState (synced) / TrainPose (output). Ownership, lifetime,
sync, render deps in TRAIN_FORMATION_BOGIE_DESIGN.md.

====================================================================
19. BOGIE
====================================================================
Decision: LOGICAL ANCHORS (not physics entities) with a light car entity
for culling/seats (ADR-004). Front/rear at bogiePos offsets; body pose
derived from the two anchors. Rationale: RTM uses bogie entities [R-I] but
browser entity/tracking/packet cost favors anchors; visuals render from
anchors.

====================================================================
20. BODY POSE
====================================================================
center = interpolate(front,rear) by |lf|/span; y = mean(bogieY);
yaw = atan2(Fx-Rx, Fz-Rz); pitch = atan2(Fy-Ry, hypot); roll = (F.roll +
-R.roll)/2; body lifted by TRAIN_HEIGHT rotated by roll (RTM updateTrainPos
[R-I]). Continuous across boundaries, S-curves, gradients, cants.

====================================================================
21. FORMATION / COUPLING
====================================================================
Ordered cars; car k at leaderDistance - k*carSpacing resolved backward
across path entries (no modulo). Coupling distance = halfLenA + halfLenB
[R-I]. Split/merge O(1). Reverse = direction flip + re-derive. This fixes
the v1 teleport bug by construction. Headline acceptance criterion
recorded (section 31).

====================================================================
22. DISTANCE-BASED MOVEMENT
====================================================================
Global path distance (scalar), route-relative and piece-local distances
derived via RailPath entries; direction + traversal history in PathPosition.
Loop / branch / reverse / switch / long train all resolvable without
teleport.

====================================================================
23. DRIVING / TRAINCONTROLLER
====================================================================
Power 1-5 (per-notch max speed), inertia, brake 1-7 (per-notch decel),
emergency (RTM EnumNotch defaults [R-I]); brake ramp (~|notch|*18 ticks);
gradient resistance from sin(pitch); signal speed clamp (SignalLevel);
reverser; door interlock; pantograph/light/horn/announcement/destination
states; cab HUD. Physics in core; performance in definitions; server-script
hooks restricted.

====================================================================
24. SIGNAL / BLOCK / INTERLOCKING
====================================================================
SignalBlock = occupancy by distance interval on a piece; owner trainId;
released by tail. SignalAspect 6..1 with speed limits [R-I]. Signal hardware
+ wire/connector/insulator + logic converters. Route locking + switch
locking. Redstone integration. RTM-core compatible; CTC/ATS/ATO layers are
extension hooks (external addons [CONFIRMED-RTM]).

====================================================================
25. STATION / OPERATION
====================================================================
Station + Platform + StopPoint (piece, localM, door side, tolerance) +
dwell + announcements; Timetable/ATO = extension subsystem (external in
RTM [CONFIRMED-RTM]); v2 provides hooks, not core ATO.

====================================================================
26. CROSSING / CATENARY / OBJECTS
====================================================================
CrossingGate (gate+lights+sound+state, signal-driven). Catenary (poles,
insulators, connectors, wire with sag, pantograph contact). Railway objects
(signal/speaker/ticket gate/signboard/light/machine/ornament/container).
Content definition separated from runtime (CONTENT_MODELPACK_DESIGN.md).

====================================================================
27. CONTENT / MODELPACK
====================================================================
ContentRegistry + definitions (Train/Rail/Signal/Machine/Wire/Object/Sound/
Animation/Script). Pack = zip with pack.json + sounds.json + Model<Type>_*
.json [R-I/C-MP]. Core unchanged to add content. Missing def -> dummy.

====================================================================
28. JSON SCHEMA STRATEGY
====================================================================
Keep RTM-compatible names where possible (trainName, trainModel2, bogiePos,
trainDistance, maxSpeed, accelerateion(s), deccelerations, sound_*, ...);
aliases for legacy (trainModel/trainTexture, seatPos->slotPos); v2-only
additions namespaced (geometry, collision, restricted scripts, pack
namespace); deprecated items documented. Future RTM pack importer possible,
license-gated (no proprietary assets).

====================================================================
29. MODEL FORMAT STRATEGY
====================================================================
v2 native format (rv2m JSON mesh: parts/materials/uv/normals, cacheable)
as runtime; OBJ/MQO import via offline converter (RTM-compatible assets
license-gated); optional debug runtime parse. No OBJ/MQO runtime in browser
(default). ADR-010.

====================================================================
30. TEXTURE / MATERIAL / LIGHTING
====================================================================
Per-material textures; AlphaBlend (transparent), Light (emissive/unlit),
OneTex [C-MP]; light textures light0(off)/light1(head)/light2(tail);
rollsign sheet via uv; livery via separate defs or useCustomColor;
texture cache budget. Details in CONTENT_MODELPACK_DESIGN.md.

====================================================================
31. SOUND / SCRIPT / ANIMATION (summary)
====================================================================
Sound: SoundDefinition event keys (sound_*), spatial loop, running/accel/
decel/brake/joint/horn/door/announcement/crossing alarm; engine separate
from content.
Script: RESTRICTED (ADR-006) - expression/state layer + declarative
animations; allow-listed API; no full JS (browser/security/determinism).
Animation: PartTransform model (move/rotate per part) state-driven + time-
driven (wheel, sway) + restricted script hooks; doors/pantograph/lights/
rollsign/crossing gate.

====================================================================
32. RENDERING (summary)
====================================================================
TrainRenderer (pose+state+parts+lights+rollsign), BogieRenderer, RailRenderer
(blocks+preview), Signal/Wire/Object renderers, model+texture caches,
interpolation, culling, LOD, emissive/transparency passes, debug overlay.
Client-only; never mutates state. RENDERING_RUNTIME_DESIGN.md.

====================================================================
33. MULTIPLAYER / PERSISTENCE (summary)
====================================================================
Server-authoritative; RailwaySync packets (JOIN_SNAPSHOT, RAIL_MANIFEST,
TRAIN_STATE, TRAIN_POSE_BATCH, SIGNAL/SWITCH/EDIT events, CONTENT_MANIFEST);
client mirror + interpolation; input C->S. WorldRailData schema v2
(pieces/nodes/switches/signals/stations/crossings/catenary/formations/
objects) with schemaVersion + v1 backup; arc tables recomputed on load;
content by defId; missing def -> dummy. v1 DataWatcher -> RailwaySync.

37. ACCEPTANCE CRITERIA
====================================================================
Rail: distance/position/yaw/pitch/roll continuity at all junctions; arc
length accuracy. Train: no teleport, no disappearing follower, spacing
<0.25m over soak, long formation stable, reverse/switch/curve/S-curve/
gradient/cant. World: chunk boundary, save/load, reload (with/without
content). Multiplayer: 2-client identical pose/state, join mid-run,
bandwidth budget. Performance: 100km route, many trains, client FPS.
Content: external pack adds types without core change; dummy fallback.
Full list in doc/testing/ACCEPTANCE_TEST_STRATEGY.md.

====================================================================
38. TEST STRATEGY / SOAK TEST
====================================================================
Tiers: math/unit (JVM), headless simulation (straight/curve/S-curve/loop/
switch/gradient/cant/long train/reverse/boundary/chunk/save-load/two-train/
deadlock), integration (build gate, 2-client, editor, perf/bandwidth).
Primary Soak Gate: 8-16 car full-scale train, >=100 laps on complex loop
(straights, sharp curves, S-curves, gradients, vertical curves, cant,
switch, boundaries, chunk crossing) with NO car disappearance, NO teleport,
spacing within 0.25m, pose continuous, switch+reverse+save/load+chunk
reload exercised. doc/testing/ACCEPTANCE_TEST_STRATEGY.md.
