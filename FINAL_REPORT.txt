9. /railsys CURRENT ARCHITECTURE
--------------------------------
Model: node/segment GRAPH + per-entity segmentId/progress (0..1).

RailGraph         - container: nodes map, segments map, switch target map,
                     train target map, occupied segment set, station node set.
                     Creates nodes/segments; NBT read/write; copyFrom mirror.
RailNode          - immutable id/x/y/z + connectedNodeIds adjacency.
RailSegment       - id, startNodeId, endNodeId, length, type, optional curveData.
                     getPoint(t) -> STRAIGHT lerp or Bezier getPoint(t).
                     length = chord for straight, 32-sample polyline approx for curve.
RailCurveData     - 6 control coordinates; cubic Bezier getPoint(t) on raw t.
RailSegmentType   - enum STRAIGHT, CURVE, SLOPE, SWITCH (SLOPE/SWITCH unused).
RailPosition      - (segmentId, progress[0..1]) value object (used sparingly).
RailSystemManager - static GLOBAL_GRAPH mirror + getGraphForWorld()/markDirty().
RailSystemSavedData- WorldSavedData "rail_system" holding the per-world RailGraph.
EntityRailVehicle - server-authoritative entity. lead car advances progress,
                     follower cars recompute from lead each tick; DataWatcher
                     syncs 9 fields; NBT 14 keys; rider controls throttle.
CommandRailSystem - /railsys dispatcher (18 subcommands), debug markers.
ItemRailWand      - 4-click Bezier creation (start, c1, c2, end).
RenderRailVehicle - colored cuboids + coupler line to next car; no textures.
RenderGlobal      - debug rail graph overlay (nodes/segments/curve) on F3.

Data flow (server):
  command/wand -> RailGraph (WorldSavedData) -> markDirty -> WorldSavedData save
  EntityRailVehicle.onUpdate (server) -> graph lookup -> segment.getPoint(progress)
  DataWatcher: trainId, carIndex, trainLength, carSpacing, isLeadCar,
               targetSpeed, speed, segmentId, progress
  EntityTracker -> S0EPacketSpawnObject(80) + standard entity packets

13. KNOWN / PROBABLE BUGS (recorded, NOT fixed)
-----------------------------------------------
  B1. Follower cars can teleport/jump at segment transitions
      (the reported disappearing/flickering issue). See section 14.
  B2. Followers always forced onto the LEADER's segment; their true
      segment is never tracked -> occupancy of the segment they still
      physically occupy is cleared too early by the leader.
  B3. Curve spacing drift: progress is raw t; distance per progress unit
      varies along a Bezier -> cars bunch/stretch on curves.
  B4. yaw look-ahead clamps at segment ends (getAheadProgress) -> near a
      node the yaw falls back to prevPos delta; one-frame yaw snaps.
  B5. No pitch -> on any vertical profile the car does not tilt.
  B6. Static GLOBAL_GRAPH shared across worlds; copy-on-change mirroring
      (full graph NBT serialize per markDirty) is fragile and O(graph).
  B7. Debug marker list is a static, not per-world; clear removes markers
      from any world (multiplayer hazard).
  B8. /railsys clear kills ALL rail vehicles in the world (clearRailVehicles),
      not just the train of the command user.
  B9. Occupancy is set only by lead car; a stopped lead at segment end
      blocks that segment indefinitely if the next segment is occupied
      (no timeout / no dwell for signals).
  B10. Route greediness can loop (oscillate) between two nodes.
  B11. Client graph absent in real multiplayer (see 15) -> vehicles rely on
      3-tick server position packets; visible stutter/teleport.
  B12. nextTrainId is a static server field scanned against loaded entities;
      after restart train IDs may collide with NBT-loaded vehicles.
  B13. entity spawn packet passes segmentId as packet data, but the client
      cannot resolve graph nodes/segments without the graph -> position
      only correct inside the same-JVM (integrated server) case.
  B14. No zero-speed sanity: follower progress uses wrap() (not clamp);
      negative results wrap near 1.0, placing followers AHEAD of the lead
      (this is the core of B1).


14. TRAILING-CAR DISAPPEARANCE ANALYSIS (priority)
-------------------------------------------------
Reported symptom:
  "When the lead car reaches a curve or crosses into another segment,
   trailing cars briefly disappear / look unnatural."

Root cause chain (EntityRailVehicle.onUpdate, follower branch, lines 134-165):

  a) this.segmentId = leadCar.segmentId;  -- follower is FORCED onto the
     leader's segment every tick, ignoring where the follower physically is.

  b) targetProgress = lead.progress +/- progressOffset;  -- offset in progress
     units = carSpacing / segmentLength, i.e. assumed linear distance mapping.

  c) modulo wrap:  while (p<0) p+=1; while (p>1) p-=1;  -- a NEGATIVE offset
     (follower is behind the leader) is wrapped to ~1.0 on the LEADER's NEW
     segment. In a closed loop the far end of the new segment lies AHEAD of
     the leader, so the follower TELEPORTS forward (possibly through a
     curve) and then slides backward until the wrap point, then resumes a
     correct trailing offset. This produces the "disappear / flicker".

  Concrete numbers (testloop: straight segment length 20, spacing 3.0,
  carIndex 1 -> progressOffset 0.15):
     leader just entered new segment at progress 0.0:
       follower = 0.0 - 0.15 = -0.15 -> wrapped to 0.85
       => follower rendered 17 blocks ahead of the leader on the new segment
     correct behavior: follower should stay ~3m behind, still on the
       PREVIOUS segment.

  Contributing factors:
    - segment-relative progress [0,1] with NO network/arc-length distance
    - no "trailing distance" model (leader world-distance minus car spacing)
    - raw-t Bezier mapping (B3) makes spacing uneven on curves
    - yaw from clamped look-ahead (B4) adds a visual snap on transition
    - coupler line distance gate (400 sq = 20 blocks) makes the coupler
      vanish when a follower jumps >20m (visual "disappearance" of coupling)
    - in split client/server, the client has no graph (B11) so movement
      depends on sparse server packets -> extra flicker
    - no bogie/car-center model; orientation is a single tangent vector

  Recommended design (NOT implemented):
    Replace "follower recompute on leader's segment" with arc-length
    trailing along the rail network:
      - define RailPath = ordered list of (segment, direction) with a
        cumulative distance offset per entry (route-aware, switch-aware)
      - leader position = (segmentId, arcOffset) where arcOffset is
        distance from segment start
      - follower i = leader arc position MINUS (i * carSpacing), resolved by
        walking backward across segments using per-segment arc length
        (segment.getDistanceForProgress / arc-length table)
      - per-car bogie anchors: front/rear bogie at car length /2 each side;
        car pose (x,y,z,yaw,pitch,roll) derived from the two bogie samples
        (yaw from chord, pitch from height delta, roll from cant)
      - keep segment-progress ONLY as a low-level per-segment lookup key,
        never as the formation/spacing authority


15. TECHNICAL DEBT
------------------
  D1. No rail-network synchronization to clients (biggest structural debt).
  D2. Global static graph + mirror copy scheme (single-world assumption).
  D3. Progress-as-distance approximation (raw t, 32-sample length).
  D4. Formation handled by per-tick leader scanning O(cars x entities).
  D5. All rendering is debug/procedural; no content pipeline.
  D6. No tests or CI for rail math / formation invariants.
  D7. Occupancy semantics too coarse (whole segment bool, leader-only).
  D8. Entity tracker rate (3 ticks) too coarse for smooth train motion.
  D9. Hard-coded numbers in the renderer (car size, spacing 3.0, etc.).
  D10. The client depends on the server-side graph through a shared static;
      Eaglercraft TeaVM single-threaded model hides this in single-player.
  D11. RailWand only makes curves, no straight-line / continuous placement.
  D12. No undo for rail edits; debug markers are not owned per rail piece.


16. RealTrainMod (RTM) FEATURE TAXONOMY
---------------------------------------
Sources: CurseForge (official), RTM Wiki (rtmwiki.kotl.io) and its GitHub
source, RealTrainModRenewed architecture. RTM is "All Rights Reserved"
(C) ngt5479 / NGTLib prerequisite, Minecraft 1.5.2-1.12.2, Forge. This

16.1 Rail / Track system
  - Marker-based placement: two markers (arrows facing) -> rail created by
    right-clicking the rail item on the markers.
  - Straight / curve / slope / switch (turnout) rail types; rail PACKS
    define rail shapes (RailRegistry / RailDefinition in Renewed).
  - Rail is world block geometry with ballast; RailCollision blocks;
    rail core block entity (LargeRailCoreBlock) owns each rail piece.
  - Rail data per piece: start/end RailPosition, direction (8 directions),
    height in 1/16 blocks, cant (roll), const speed-limit fields, precise
    position overrides, neighbor detection, redstone input.
  - Curves are cubic Bezier with ARC-LENGTH parameterization
    (index/split proportional to distance), slope/pitch from height,
    roll (cant) per sample.
  - Turnouts / switches: RailMapSwitch, SwitchType; switch state stored in
    the rail, driven by redstone or signal state.
  - Rail preview renderer before placement; copy/copy-rail tools.
  - Track protection: /protect <ID> key prevents accidental breakage.

16.2 Train / rolling stock
  - Full-scale (1:1, 実寸大) 3D cars from OBJ/MQO models.
  - TrainEntity + CarEntity + TrainBogieEntity (bogies are separate
    entities/anchors) + seats (TrainSeatEntity), floors.
  - Formation management: Formation / FormationEntry / FormationManager;
    coupled chain via leader/follower UUIDs; coupled-formation sync from
    head; dynamic length changes.
  - Coupling / uncoupling with a "crowbar" (バール) tool.
  - Movement: notch-based physics (applyNotchPhysics): reversible notches,
    per-notch max speed, acceleration, brake deceleration, air brake.
  - Distance-based travel along rail (travelAlongRail), bogie-pair
    advance by METERS along path (advanceBogiePairAlongPath), trailing
    anchor derivation by span distance (deriveTrailingAnchor), teleport /
    warp guards for rail joints.
  - Pose from bogie samples: yaw from front/rear chord, pitch from height,
    roll/cant lean; body center offset; interpolation handler on client.

16.3 Operation / infrastructure
  - Driving: enter cab (click wheels at front), W/S staged throttle,
    reverser, brake notch, doors, interior lights, horn, pantograph up/down,
    in-car announcements, destination/type signs (rollsign).
  - Signals: signal blocks/entities, redstone + wire connections (insulator
    + wire placement), signal state propagation, signal control via
    SignalControllerMod / ATSAssistMod / WebCTC (external).
  - Level crossing (踏切): gates + state; configurable models.
  - Stations: station structures/props, stop behavior, timetables
    (community automation e.g. RealTrainMod-Automation with Oudia).
  - Catenary / overhead wire: insulators + wires (string/connecting),
    pantograph interaction, invisible-wire trick.
  - Ballast / track facilities; signboards; a wide catalog of props
    (poles, buildings via ngto/schematic import through MCTE).
  - Rail network spanning hundreds/thousands of km is achievable.

16.4 Content / addon pipeline
  - Addons / model packs: JSON configs (model-config, train-config,
    vehicle-base-config, resource-config, rollsign), custom models,
    scripts (JavaScript), sound libraries (SoundLib), bundled packs.
  - Community content: vehicles, rails, signals, stations, props, cars,
    ships, aircraft.
  - Licensing: RTM itself is All Rights Reserved; addons vary. For this
    project: implement functionality with original code/models only.
    Do NOT bundle RTM jars, models, textures, or sounds. If community
    content is later desired, verify each pack's license individually.

16.5 Multiplayer / persistence
  - Forge servers: rail world-state persisted per world; trains synced via
    entity packets + script data sync; client prediction/interpolation.

18. FINAL TARGET ARCHITECTURE (design)
--------------------------------------
Proposed package layout (names kept consistent with existing code where
possible; extensions new):
  net.minecraft.rail.*          (existing: RailGraph, RailNode, RailSegment, ...)
  net.minecraft.rail.path.*     (new: RailPath, PathDistance, PathPosition)
  net.minecraft.rail.track.*    (new: RailPiece, RailRegistry, RailBallast)
  net.minecraft.rail.math.*     (new: ArcLengthCurve, TrackMath)
  net.minecraft.rail.signal.*   (new: Signal, SignalBlock, SignalController)
  net.minecraft.train.*         (new: Train, TrainFormation, TrainCar, Bogie)
  net.minecraft.station.*       (new: Station, Platform, StopPoint, Timetable)

Responsibilities (data ownership, dependencies, sync, render, tick):

  RailNetwork (was RailGraph)
    - owns nodes, segments, switch state, stations, routes
    - exposes "distance resolver": resolve(PathPosition) -> (segment,progress)
      and resolve(distance) -> (segment,progress) via arc-length tables
    - owns per-segment arc-length lookup table (progress<->meters)

  RailSegment (kept)
    - add: arc-length table (build once per segment; length exact)
    - add: slope/cant profile; direction-aware traversal
    - expose getPosAtMeters(m), getYawAtMeters, getPitchAtMeters,
      getRollAtMeters (or keep index/sample API)

  RailPath / PathDistance
    - a walkable ordered route: [ (segmentId, direction, startM, endM) ]
      (switch-aware; produced once when a train enters a node)
    - cumulative distance so a train has a scalar "path distance"
    - traversal: distance += speed*dt; walk across segments

  RailPiece / RailRegistry (new, track-as-content)
    - each placed rail is a world "piece" (core block entity + collision),
      owns its RailMap geometry; registry maps pack definitions
    - RailMap geometry provides: length, points, height, yaw/pitch/roll per
      arc-length sample (clean-room port of the *concept*, not RTM code)

  TrainFormation (new)
    - owns the ordered car list; head car authoritative
    - update(): head car advances path distance; each following car placed
      at headDistance - (i * carSpacing) resolved across the path
    - owns coupling state, train id, passenger seat mapping

  TrainCar / Bogie (new)

  Station / Platform / StopPoint / Timetable (new)

  Crossing / Catenary (new)

  RailwayPersistence (new)

  RailwayNetworkSync (new)

  RailwayRenderer (extend RenderRailVehicle / new)

20. DISTANCE-BASED MOVEMENT DESIGN (the core change)
---------------------------------------------------
Replace "segment-progress formation" with network-arc-length movement.

  20.1 Arc-length per segment
       Build cumulative distance table per segment once (on creation or
       load): meters[i] for i in 0..split. For curves use arc-length
       reparameterization so index -> equal distance (RTM's concept,
       original implementation). Straight: meters = progress * lengthM.

  20.2 Leader motion
       leader.pathDistance += direction * speed * dt
       Resolve pathDistance -> (segmentId, progress) by walking the path
       entries. At a path end without continuation, choose next segment by
       switch target > route (A* on graph) > first connected, appending a
       new path entry (continuous distance).

  20.3 Follower placement (fixes the disappearance bug)
       For car i: targetDistance = leader.pathDistance - (i * carSpacing)
       Walk backward from the leader's path entry subtracting each
       segment's length until targetDistance lands inside a segment.
       That (segmentId, progress) is the follower's position. No modulo
       wrap. When the leader is in segment N, cars 1..k naturally stay on
       N-1, N-2, ... — no teleport, spacing always in meters.

  20.4 Pose from bogies
       Each car has front/rear bogie at +/-bogieOffset around the car
       center (path distance). Sample the rail at both bogie distances:
         yaw   = atan2(front.z-rear.z, front.x-rear.x)
         pitch = atan2(dy, chordLen)
         roll  = cant at center
       centerY = mean(bogieY) (+ body offset); position interpolated.

  20.5 Switch/routing integration
       Path building consults switch state when reaching a node; the whole
       formation shares the same path so all cars follow the same route
       (this also fixes cars splitting across turnouts).

  20.6 Reverse
       Reversing = negate direction; path is traversed backward; cars
       re-derive by adding i*carSpacing ahead when reversing.

  20.7 Vertical
       Slope segments get a height profile; pitch derived from bogies;
       supported as first-class, not a special case.

  Feasibility vs current structure:
    - RailGraph/RailSegment/NBT remain; we ADD the length table and a path
      layer. EntityRailVehicle becomes a thin entity delegating to
      TrainFormation/TrainCar math (server) and Interpolation (client).
    - This preserves existing commands and saved graphs (backward compat).
