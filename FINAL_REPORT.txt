10. RTM OVERVIEW
----------------
RealTrainMod (RTM) by ngt5479 is a Forge mod for Minecraft Java Edition that
adds a full railway platform: full-scale 3D railway vehicles, rails,
signals, catenary, crossings, station equipment, and a large catalog of
objects/props, PLUS a content-addon system (ModelPacks) with JSON configs,
OBJ/MQO models, textures, sounds, and JavaScript scripts. [CONFIRMED-RTM]

Core facts:
  - MC versions: primarily 1.7.10 and 1.12.2 (also 1.10.2; early 1.5.2-1.6.x).
  - Prerequisite: NGTLib (by same author). [CONFIRMED-RTM]
  - License: All Rights Reserved. Addons' licenses vary. [CONFIRMED-RTM]
  - Unofficial companions: KaizPatchX (1.7.10 fork bundling NGTLib+MCTE),
    fixRTM (1.12.2 bugfix), RealTrainModUnofficial (1.21.1 port),
    RealTrainModRenewed (modern rewrite). [CONFIRMED-RTM/Tier2]

Platform split (Core vs Content):
  CORE (in RTM itself): rail placement/math, train/formation/bogie runtime,
    driving/notch physics, signal/wire/electricity runtime, crossings,
    machine runtime, model pack loading/registry, renderer, networking,
    persistence, seat/player handling.
  CONTENT (via ModelPacks): all vehicle/rail/signal/object MODELS and their
    JSON performance/behavior configuration, textures, sounds, scripts.

12. NGTLib RELATIONSHIP
-----------------------
NGTLib provides the shared foundation: model loading (OBJ/MQO/NGTO),
resource/pack handling, math, NBT utilities, sound player, data map,
permissions, and the "installed object" base machinery. RTM adds rail/train/
signal/electric domain logic on top. KaizPatchX bundles NGTLib+MCTE into one
jar and is a drop-in RTM replacement for 1.7.10. [CONFIRMED-RTM/Tier2,
REFERENCE-IMPLEMENTATION]
=> Phase -1 implication: a Web/Eaglercraft port needs an equivalent "library"
layer (math, model loader, pack loader, data map, sound) before the rail
domain can be clean.

14. TRAIN / FORMATION SPECIFICATION
-----------------------------------
- A Formation is an ordered list of trains (FormationEntry {train,pos,dir}).
  One control car drives; direction + speed are shared. [REFERENCE-IMPLEMENTATION]
- Coupling: connecting two trains creates one Formation; disconnecting
  splits it. Coupling distance = trainDistance_A + trainDistance_B. [R-I]
- Movement update (front car only): for each car in order, position car i
  from car i-1's bogies; front car advances by speed. [R-I]
- TrainState (synced) covers: train_dir, notch, signal, door, light,
  pantograph, chunk_loader, destination, announcement, direction (front/
  center/back), interior_light. [R-I]
- Chunk loader state exists so long trains keep chunks loaded. [R-I]
=> This is the RTM "formation = ordered cars, each derived from previous"
model; distinct from the current /railsys trainId/carIndex with independent
followers (relevant Phase -1 input).

15. BOGIE SPECIFICATION
-----------------------
- Bogies are RUNTIME positioning anchors, not just visuals. Each train has
  two bogie entities (front/rear) created at spawn. [REFERENCE-IMPLEMENTATION]
- Bogie placement: bogiePos [[0,0,+L],[0,0,-L]] relative to train center;
  default L=7.125m. Train moves by advancing the FRONT bogie along the rail
  (updateBogiePos by speed distance), then positioning the REAR bogie
  trainLength behind, then deriving the body. [R-I]
- Body pose from bogie chord (updateTrainPos): [R-I]
    x = lerp(front,rear, |lf|/|lf-lb|), y = mean(bogieY)
    yaw   = atan2(front.x-rear.x, front.z-rear.z)
    pitch = atan2(y0, sqrt(x0^2+z0^2))   (gradient tilt)
    roll  = (bogie0.roll + -bogie1.roll)/2  (cant from bogie roll)
    body offset by TRAIN_HEIGHT along roll (cant shift).
- Following cars: front bogie positioned at coupling gap distance from the
  PREVIOUS car's rear bogie (disBogie = couplingDist - halfLengths). [R-I]
- Bogies also derive from the body (updateBogiePos) to correct drift. [R-I]
- Bogies rotate (wheel rotation, bogie yaw on curves). [R-I]
=> Phase -1: distance-accurate bogie-anchored body pose is the reference
model; matches the direction recommended in the prior phase analysis.

16. VEHICLE SCALE / DIMENSIONS
------------------------------
- RTM is 1:1 real scale; 1 Minecraft block = 1 metre. [CONFIRMED-RTM]
- Default half-length trainDistance = 10.125m (=> ~20.25m car) [R-I]
- Default bogie spacing ~14.25m (7.125 x2) [R-I]
- Default width/height collision 2.75 x 1.25 [R-I]
- Real-vehicle pack examples (community knowledge, INFERRED):
    10m級 single-unit (e.g. tram/mini)  trainDistance ~5
    16m級  short EMU               ~8
    18m級  20m-class EMU (commonly used) ~9-9.5
    20m級  JNR 20m EMU            ~10
    Locomotives similar 18-20m; freight cars shorter; trams narrower.
  Exact numbers are per-pack config (trainDistance/bogiePos); no single
  canonical table exists in official docs [INFERRED].
- Units: positions/offsets are metres (blocks); legacy seatPos used 1/16
  block units (0.0625); rail height steps use 1/16 block. [C-MP]

17. DRIVING SPECIFICATION
-------------------------
- Cab: click the front wheels/bogie to enter the driver seat; driver pos
  from playerPos[dir]. [CONFIRMED-RTM (getting-started), R-I]
- Notches (EnumNotch): accel 1..5 (max speed 0.36/0.72/1.08/1.44/1.80
  blocks/tick), inertia 0, brake 1..7 (dec -0.0005..-0.0035), emergency
  brake -8 (-0.01). Brake application uses a brakeCount ramp
  (notch*-18 ticks to full brake). [R-I]
- Acceleration config from JSON (accelerateions/maxSpeed/deccelerations);
  server script may override if useVariableAcceleration/Deceleration. [C-MP]
- Gradient effect: extra deceleration/gravity from rotationPitch. [R-I]
- Controls (1.7.10/1.12.2, from Wiki): S=power, W=brake (staged notch
  steps); reverser, EB (emergency), horn, door, pantograph, lights, etc.
- Signal influences speed: signal level clamps speed to its limit
  (SignalLevel.getSpeed); ATS chime/bell sounds exist. [R-I]
- HUD shows speed/notch; destination/announcement via TrainState. [R-I]

18. RAIL GEOMETRY SPECIFICATION
-------------------------------
- Rail geometry is per-piece, not a graph: each placed rail is a RailMap
  between two RailPositions. [CONFIRMED-MODELPACK + R-I]
- RailMap abstraction (from rail placement/math): [R-I]
    getLength()             piece length (3D, includes slope)
    getRailPos(split,index) -> [z,x] sample at arc-length-like split
    getRailHeight(split,index), getRailYaw, getRailPitch, getRailRoll(=cant)
    getNearlestPoint(split,x,z)  nearest sample to a world point
    canConnect(other)       endpoint connectivity
  This is EXACTLY the "sample any world distance -> x/y/z/yaw/pitch/roll"
  concept the current /railsys lacks.
- RailPosition: {blockX,Y,Z, direction(0..7 = 45deg steps), height (1/16
  block), switchType, anchorYaw, anchorPitch, anchorLengthHorizontal/
  Vertical, cantCenter/cantEdge/cantRandom, constLimitHP/HN/WP/WN,
  precise position overrides} [R-I / CONFIRMED-MODELPACK for const fields]
- Curve: cubic Bezier on X/Z with arc-length reparameterization; split ~
  length*32 (max 384 render); slope from control points. [R-I]
- Straight: RailMapBasic with 8 directions. [R-I]
- Slope: RailMapSlope slopeType 0..3 => length 16/8/4/2 blocks, fixed
  pitches 3.576/7.125/14.036/26.565 deg; height encoded in block metadata
  (1/16-block steps). [R-I]
- Switch: RailMapSwitch (RailMapBasic subclass) with startDir/endDir and
  open/closed state. [R-I]
- Cant (roll): per-sample roll; body leans; const limit fields bound ballast.
- Ballast: created as blocks along the rail width (ballastWidth 1/3/5 m),
  per block-metadata height; rails are block structures (BlockLargeRail*
  + TileEntityLargeRail*), core block owns the piece. [C-MP + R-I]
- Rail properties: speed limit, allowCrossing, defaultBallast. [C-MP]

19. RAIL PLACEMENT SPECIFICATION
--------------------------------
- Place two Marker blocks (or a markerSwitch) with arrows facing; right-click
  a rail item to open the marker GUI and place the rail. [CONFIRMED-RTM]
- Marker encodes RailPosition; markerSwitch adds switchType flag. [R-I]
- Placement validation (canPlaceRail): obstacles, air, marker, other rail
  base blocks; creative bypass. [R-I]
- The rail creates its block list (ballast + rail base blocks) and sets the
  core TileEntity owning them. Breaking removes owned blocks only. [R-I]
- Preview: rendered rail preview before placement (client). [CONFIRMED-RTM
  (observed), R-I in Renewed]
- Copy/undo/remove/edit tools exist in creative/marker GUI. [INFERRED]

20. SWITCH / TURNOUT SPECIFICATION
----------------------------------
- Switch = rail piece whose geometry branches; type derived from marker
  pattern in RailMaker: [R-I]
    3 points, 1 switch   -> SwitchBasic (single turnout)
    4 points, 2 switches -> SwitchSingleCross
    4 points, 4 switches, two same dir -> SwitchScissorsCross
    4 points, 4 switches otherwise     -> SwitchDiamondCross
- Switch state (open/closed) toggled by redstone or signal/electricity,
  stored in the rail TileEntity. [R-I]
- Trains traverse the chosen branch; whole formation follows same route.
- Reverse traversal supported; state saved/loaded; synced via TileEntity
  state. [INFERRED]

21. SIGNAL / BLOCK / INTERLOCKING SPECIFICATION
-----------------------------------------------
- Signal = installed object (BlockSignal + TileEntitySignal) whose model
  and lights come from a ModelPack (SignalConfig). [C-MP + R-I]
- Signal levels (SignalLevel): [R-I]
    HIGH_SPEED_PROCEED(6) speed 1.2-1.5, PROCEED(5) 0.9-1.2,
    SLOW_DOWN(4) 0.6-0.9, CAUTION(3) 0.3-0.6, VIGILANCE(2) 0.3-0.6,
    STOP(1) 0.  (speed = km/h / 72 in blocks/tick)
- Signal state flows over the ELECTRICITY system: wires between connectors
  (Relay/Input/Output) and insulators; signal converters (BlockSignalConverter,
  SignalConverterType) implement logic (NOT/AND/OR, signal-to-redstone etc.).
  [R-I]
- Train detection: rail redstone/occupancy via TileEntityLargeRail (rail
  outputs signal level); train speed limited by detected signal level;
  ATS chime/bell; automatic braking at STOP. [R-I]
- External addons: ATSAssistMod, SignalControllerMod, WebCTC provide CTC/
  ATS/ATO layers on top. RTM itself supplies detection + speed limit +
  signal-to-rail wiring. [CONFIRMED-RTM (Wiki related-mods)]
- Interlocking tables are NOT in RTM core [INFERRED]; route setting is
  switch state driven by redstone/signals.

22. CATENARY / WIRE SPECIFICATION
---------------------------------
- Electricity model: BlockElectricalWiring + EntityElectricalWiring +
  WireManager; wires connect Connectors (Relay/Input/Output) and Insulators.
  Wires sag per WireConfig (deflectionCoefficient, lengthCoefficient,
  sectionLength, yOffset). [R-I]
- Overhead catenary is represented as wires between insulator/connector
  blocks; pantograph (pantoPos) interacts for cosmetic/electrical state
  (pantograph up/down TrainState). [CONFIRMED-RTM (tips: insulator + wire
  usage), R-I]
- Placement: place insulator/connector blocks, then stretch wire between
  them (right-click workflow). "Invisible wire" trick documented in Wiki
  tips. [CONFIRMED-RTM]
- Wire is a ModelPack type (ModelWire). [C-MP]

23. LEVEL CROSSING SPECIFICATION
--------------------------------
- Crossing = Machine with gate animation, flashing lights, alarm sound
  (TileEntityCrossingGate: lightCount toggle, sound_Running loop, MachineType
  .Gate). [R-I]
- State driven by redstone/electricity (signal system); closes before train
  arrival via signal wiring; model from ModelPack (MachineConfig). [R-I]
- Sound + lights + gate parts animate; synced as TileEntity/machine state.
  [R-I]

24. STATION / PLATFORM SPECIFICATION
------------------------------------
- Stations are NOT a core train-stop system; stopping is done by signals/
  redstone and manual driving. Platforms/buildings/gates/ticket machines/
  speakers are Installed Objects (ModelMachine / ModelOrnament / specific
  blocks: BlockTicketVendor, BlockSpeaker). [CONFIRMED-RTM (props catalog),
  R-I]
- Stop-position control is achievable via signals + ATO-style addons;
  automatic operation (timetables) via community addons (e.g. RealTrainMod-
  Automation with Oudia). [CONFIRMED-RTM (Wiki)]
- Announcements: sound_Announcement [[name,sound]] on trains; station
  speakers for station announcements. [C-MP]

25. RAILWAY OBJECT SPECIFICATION
--------------------------------
Installed Objects (installed on/off rails, from ModelPacks): [C-MP + R-I]

26. MODELPACK OVERVIEW
----------------------
- A ModelPack (addon / model pack) is a zip or jar (or unpacked directory)
  placed in the Minecraft `mods` folder. [CONFIRMED-RTM (Wiki install), R-I]
- The pack contains: JSON configs named `Model<Type>_<name>.json`, plus
  model/texture/sound/script assets. Config TYPE is derived from the FILE
  NAME prefix: `ModelTrain_*.json`, `ModelRail_*.json`, `ModelSignal_*.json`,
  `ModelVehicle_*`, `ModelMachine_*`, `ModelOrnament_*`, `ModelContainer_*`,
  `ModelWire_*`, `ModelConnector_*`, `ModelFirearm_*`, `ModelNPC_*`. [R-I]
- Loading: NGTFileLoader scans mods dir (recursively incl. inside zips,
  SJIS/MS932 fallback) for files matching `Model.*\.json`, registers each
  model set by type. [R-I]
- `pack.json` provides {name, homepage, updateURL, version}; update text
  file "addon:version" per line. [C-MP]
- `sounds.json` maps "folder.file" keys to sounds. [C-MP]
- Multiple packs coexist; duplicate names conflict (version precedence). [R-I]

27. MODELPACK DIRECTORY STRUCTURE
---------------------------------
Canonical layout (from JSON docs + loader behavior) [CONFIRMED-MODELPACK + R-I]:
```
mods/
  MyPack.jar  (zip)                     <- the pack itself
    ModelTrain_mycar.json               <- config at pack root (any depth)
    ModelRail_myrail.json
    pack.json
    sounds.json
    assets/
      minecraft/                        <- resource domain "minecraft"
        models/   mycar.mqo, myrail.obj ...
        textures/ train/mycar.png, rail/myrail.png, gui/..., icon/...
        sounds/   train/mycar_a.ogg ...
        scripts/  render/render.js, sound/sound.js, server/server.js ...
```
- modelFile paths in JSON are relative to `assets/minecraft/models/` [C-MP].
- texture paths are relative to `assets/minecraft/textures/` [C-MP].
- Sound paths resolved as resource locations "domain:folder/file" (rtm:
  prefix auto-added when missing) [R-I].
- Nested archives: supported inside packs (findFileInZip recurses) [R-I].
- Non-ASCII (SJIS) filenames handled via MS932 re-read [R-I].
(Exact domain ("minecraft" vs "rtm") for model assets is UNKNOWN for all
versions; JSON docs state assets/minecraft/models.)

    "AlphaBlend,Light,OneTex"; light textures xxx_light0(off)/light1(head)/
    light2(tail). [C-MP]

30. OBJ SPECIFICATION
---------------------
- Wavefront OBJ with MTL; supports v/vt/vn and faces v, v/vt, v//vn, v/vt/vn;
  quads supported (GL_QUADS path) - required for RTM models. [R-I]
- Groups: g/o names become part names referenced by parts config (objects).
- Materials parsed from MTL; texture per material from JSON textures array.
- Smoothing threshold ~60deg (SMOOTHING const). [R-I]
- Accuracy "LOW"/"MEDIUM" selects vertex packing. [C-MP]
- Origin: model origin = train/bogie center; forward = +Z? (to confirm in
  Phase -1). Coordinate handedness/culling per doCulling. [INFERRED]

31. MQO SPECIFICATION
---------------------
- Metasequoia (.mqo) is the primary Japanese-modeller format; RTM parses
  object/vertex/face/material sections; groups -> parts. [R-I]
- Supports V(..) vertex indices, UV(..), M(..) material per face; mirror
  faces for mirrored models. [R-I]
- Mqoz = compressed variant. [R-I]
- MQO authoring is the community standard for RTM vehicles. [C-RTM/Tier2]
- Same JSON texture binding as OBJ (materials by name). [C-MP]
- NGTO (ngt's own format) also loadable (scale key). [C-MP]

32. TEXTURE SPECIFICATION
-------------------------
- PNG textures (non-power-of-2 likely; RTM loads via texture manager). [R-I]
- Materials map to textures via JSON textures array [["material","path"]].
- Light textures: xxx_light0(off)/xxx_light1(head)/xxx_light2(tail) appended
  automatically for lights. [C-MP]
- AlphaBlend option enables transparency; Light option emissive; OneTex.
- useCustomColor tints in-game without changing files. [C-MP]
- rollsign uses a sheet texture mapped by uv {uMin,uMax,vMin,vMax} onto
  quads defined by pos (4 points). [C-MP]
- Repaint/livery variation: separate JSON configs sharing one model file but
  different textures = the standard repaint approach. [INFERRED]

33. SOUND SPECIFICATION
-----------------------
- Sound events keyed by JSON sound_* fields; values are resource locations
  "domain:folder/file" (rtm: auto-prefixed). [R-I]
- sounds.json maps keys (folder.file) to files with category neutral. [C-MP]
- Sound scripts (soundScriptPath) drive procedural/layered sounds; running
  sounds loop; volume/pitch controlled per event. [R-I]
- Joint sounds (sound_Joint, sound_JointReverb) triggered by rail joints
  (wheelbase-dependent, jointDelay). [C-MP]
- Crossing alarm uses machine sound_Running loop + lights. [R-I]
- Announcements: [[name,sound]] selectable. [C-MP]

34. SCRIPT SPECIFICATION
------------------------
- JavaScript (Nashorn in 1.7/1.8 Forge; TeaVM equivalent needed for Web).
- rendererPath: per-frame render control (part transforms, doors, panto,
  rollsign animation). [C-MP]
- soundScriptPath: audio engine logic. [C-MP]
- serverScriptPath: server-side behavior, may override accel/decel
  (useVariableAcceleration/Deceleration), control custom buttons, read
  TrainState/signal/speed/time. [C-MP/R-I]
- guiScriptPath: custom GUI. [C-MP]
- DataMap gives scripts a typed key/value state per instance. [R-I]
- Script sandboxing / memory / async concerns for Web/Eaglercraft:
  => Phase -1 design question (sandbox, no JVM Nashorn, TeaVM JS interop).

35. ANIMATION SPECIFICATION
---------------------------
- Door open/close: parts + transform arrays (translation) per door_left/
  door_right; states Door_OpenLeft/Right/All. [C-MP/R-I]
- Pantograph up/down: parts + transforms. [C-MP/R-I]
- Bogie rotation, wheel rotation (wheelRotationSpeed), body roll (sway),
  cant. [R-I]
- Rollsign: uv-mapped sheet animation (doAnimation). [C-MP]
- Type sign/destination: rollsign index; custom buttons. [C-MP]
- Script-driven animations via renderer scripts. [C-MP]
- Crossing gate + lights + flashing. [R-I]
- No formal timeline; per-part transform JSON + script callbacks. [C-MP]

36. RENDERING SPECIFICATION
---------------------------
- Trains: body model + bogie models rendered separately (RenderTrain/
  RenderBogie); pose from bogie anchors; roll from cant; part transforms
  from state; lights emissive; rollsign/type signs; culling by renderAABB.
  [R-I]
- Rails: rendered as block structures (BlockLargeRail renderer + TileEntity)
  + ballast blocks; switch/slope variants; marker preview. [R-I]
- Wires: line rendering between connectors (EntityElectricalWiring /
  RenderElectricalWiring) with sag. [R-I]
- Signals/objects: ModelSet renderers + light textures + rotateBody. [R-I]
- Installed Objects (machines/ornaments): tile/entity renderers. [R-I]
- Interpolation: entity interpolation for trains/bogies on client. [R-I]
- Model/texture caching, LOD/distance culling (renderAABB), accuracy-based
  vertex packing. [C-MP/R-I]
- Transparency: AlphaBlend materials; emissive: Light materials. [C-MP]

37. MULTIPLAYER / NETWORK SPECIFICATION
---------------------------------------
- Server authority for train physics and rail/switch/signal state. [R-I]
- TrainState synced via packets (PacketSetTrainState) for door/light/panto/
  notch/signal/direction/destination/announcement. [R-I]
- Bogies/trains are entities tracked normally; rider/seat sync via vanilla
  mount + playerPos transforms. [R-I]
- Rail pieces are blocks/TileEntities => state synced via vanilla chunk/
  tile-entity sync (switch state, signal level, machine data). [R-I]
- ModelPacks must be installed CLIENT-side (models/textures); server needs
  configs for physics/permissions. [CONFIRMED-RTM (community), R-I]
- Wire/electricity state synced through TileEntities. [R-I]
- PacketModelPack: server can push model packs to clients. [R-I]
- Client prediction: minimal; entity interpolation handles motion. [R-I]

38. PERSISTENCE SPECIFICATION
-----------------------------
- Rails: block/TileEntity NBT (RailPosition + state + core ownership);
  saved per-world via chunk data. [R-I]
- Trains: entity NBT + Formation NBT (Formation.readFromNBT/writeToNBT with
  entries; train UIDs). [R-I]
- Formation persistence restores coupling order after reload. [R-I]
- ModelPack identity stored by config name; missing pack on load = fallback
  dummy model (graceful). [R-I]
- Version migration for NBT (e.g. v34-compat in Connection). [R-I]
- Chunk loading: trains request chunk loads (chunk_loader state). [R-I]

44. PHASE -1 DESIGN QUESTIONS (candidates + points only, no decisions)
----------------------------------------------------------------------
1. Coordinate/scale: adopt 1 block = 1 m everywhere (matches RTM).
2. Rail representation: piece-based RailMap + markers vs graph; and whether
   to keep /railsys graph as a routing overlay (recommended: both layers).
3. Arc-length sampling: table-based per piece (split ~ len*32) + nearest-
   point search + distance<->progress resolver.
4. Vertical: slope types (0..3 gradients) and 1/16-block height units;
   body pitch from bogie delta.
5. Cant: per-sample roll + body lean + ballast const limits.
6. Bogie model: bogies as ENTITIES vs pure anchors in a formation solver.
   (RTM uses bogie entities; TeaVM cost must be weighed.)
7. Formation: chain ordering (car i from car i-1) with coupling distance =
   sum of half-lengths; trainDirection; reverse.
8. Notch/physics: exact EnumNotch table + per-notch JSON overrides + brake
   ramp; signal speed clamp (SignalLevel).
9. Content schema: ModelSource JSON + file-name type prefix + pack.json +
   sounds.json; registry with name uniqueness + version precedence.
10. Model formats for Web: OBJ/MQO runtime parse vs pre-conversion pipeline
    (TeaVM memory/perf); NGTO optional.
11. Script engine on Web: sandboxed JS in Eaglercraft (no Nashorn);
    renderer/sound/server script parity vs restricted subset.
12. Multiplayer: server authority + TileEntity-style state + TrainState
    packets; client-side pack requirement; pack push.
13. Persistence: NBT equivalent (world data) for rail pieces + formations;
    version migration; chunk-load keepalive for long trains.
14. Asset/licensing policy: original/CC assets only; a pack import pipeline
    that rejects proprietary assets by policy.
15. Rail block/collision & ballast rendering cost in TeaVM.
16. Marker GUI + model selector UX on Web (reuse /weui-style pattern).
17. Interaction with existing WorldEdit/terrain editing (no shared deps).
18. Long-train entity count vs Web performance budget.
19. Rail network at hundreds of km: spatial indexing, per-piece activation.
20. Whether RTM parity includes EXTERNAL-ADDON features (CTC/ATO) or only
    core RTM taxonomy.
