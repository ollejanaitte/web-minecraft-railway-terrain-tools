2. Visual Validation 遅延の原因（調査結果）
====================================================================
実体: run-validation.sh / run-validation-workflow.sh /
      validation_workflow.mjs / 各Phaseの *_acceptance.mjs
      （headless Chrome + Eaglercraft 起動 → ワールド作成 → チャット操作
        → スクリーンショット取得 → 画像判定）

遅延要因（複合）:
1. 運用・テストルール: 通常開発ループで毎回FULL（ゲーム起動）を実行。
   Phase 1.1以降は主要な数値検証が harnessTest（純JVM・実測4秒）で可能なのに
   利用されておらず、実質毎回ゲーム実機確認へ行っていた。
2. 運用: Phase 毎にFULLを2〜3回実行（R16: 3回, R17: 2回）。失敗時は
   メニュー回復レース起因でリトライし、時間が倍増していた。
3. 実装: R16/R17 acceptance.mjs が headless 時に SwiftShader（ソフトウェア
   描画）を使用。Phase 0.2で確立した HW Vulkan（NVIDIA GTX 1050）から逸脱。
   高CPU（99〜658%相当）・フリーズ・ハングにより失敗率が上がっていた。
4. 安全対策: シェルレベルに全体タイムアウトが無く、ハング時に長時間滞留し得た。
5. 固定スリープ: ワールド入場後20秒、スクリーンショット前2.5秒など。

実測（R17 acceptance を同一スクリプムで比較）:
- HW Vulkan: 194秒（PASS）
- SwiftShader: 209秒（PASS）
- acceptance は固定スリープ・チャット待機が主体のため単発の壁時計は近い。
  HW Vulkan の実質的効果は CPU負荷低減・フリーズ/ハング起因の失敗・リトライ減少
  （安定化）。遅延の主因は「開発ループでFULL実行＋失敗リトライ＋Phase毎複数回」。

3. Visual Validation の設計問題か、運用・テストルール問題かの結論
====================================================================
- Visual Validation（実機スクリーンショット）方式自体は有用で正しい。廃止しない。
- 主因は運用・テストルールの問題:
  (a) FAST な代替（harnessTest）が開発ルールに組み込まれていなかった
  (b) FULL を毎回・複数回・リトライ込みで実行していた
  (c) 非標準の GPU パス（SwiftShader）を使用し失敗率が上がっていた
  (d) 全体タイムアウトが無くハング時に滞留した
=> 設計（方式）は妥当。運用とスクリプトの GPU 指定・安全対策の問題。

7. 日本語が表示されなかった原因（調査結果）
====================================================================
結論: 現行ビルドでは日本語表示は正常に動作している。

確認内容:
- EPK 解析（自作デコンパイラ）: 
  - font/glyph_sizes.bin (65536B, U+3042 あ=0x0F 等 日本語グリフ幅データ)
  - textures/font/unicode_page_*.png (日本語ページ 0x30-0x5f 等 実グリフあり)
  - ja_JP.lang (140KB)
  - いずれも正しく梱包済み（最初期コミット 784a776d から追跡）。欠落なし。
- 描画経路: FontRenderer.renderUnicodeChar が日本語を描画。
  EaglerFontRenderer は ASCII のみ最適化し、日本語を含む文字列はバニラ経路へ
  正しくフォールバック。
- 実機確認（headless Chrome + HW Vulkan）:
  - チャット入力欄「日本語テスト 鉄道 車両 接続 分岐器」:
    フォントソースとのピクセル一致 IoU = 1.000（全15グリフ完全一致）
  - 送信メッセージのチャットログ: 15/16グリフで IoU = 1.000

推測される本来の原因:
- 過去のビルド/状態でフォント資産が未梱包だった、または
- デスクトップ日本語IMEの確定文字（compositionend）がゲームに届かず
  「日本語が入力できない・出ない」ように見えた（表示自体は正常）、または
- 誤認

8. Unicode対応内容（実施した修正）
====================================================================
表示は正常なため表示コードの変更は不要だった。入力側の欠陥を修正:
- src/teavm/java/.../PlatformInput.java:
  window に `compositionend` リスナーを追加。IME確定文字列（event.data）を
  既存の貼り付け経路 pastedStrings → CLIPBOARD_PASTE → GuiTextField.writeText
  へ投入（ゲーム毎tickのポーリングでフォーカス中の入力欄へ挿入）。
  @JSBody で event.data を取得（TeaVM JSO API に CompositionEvent が無いため）。
- 変換中プレビュー（compositionupdate）は意図的に未対応（確定時のみ挿入し、
  変換中文字の混入を防止）。
- 検証: 合成 CompositionEvent(data=日本語) を window へ dispatch し、
  チャット入力欄へ「日本語」が挿入・描画されることを実機確認（グリフ形状一致）。
- CDP の Input.imeSetComposition / insertText は canvas ページではイベントが
  発火しないため、実ブラウザ相当の合成イベントで検証した。

日本語最小確認手段:
- doc/testing/phase1_r17_5/unicode_font_test.mjs
  （run-full-gate.sh 経由、実測約70〜100秒。ワールド作成→チャット日本語入力・
   送信→スクリーンショット。レール構築なしの軽量構成）
